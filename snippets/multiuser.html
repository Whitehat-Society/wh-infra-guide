Web · HTTP

Shared pods, load-balanced per request

  • NGINX spreads requests across the 2 replicas. No session affinity is configured.
  • Rate limits, per client address: 20 rps, burst ×1, 15 concurrent connections. Excess requests get 503.
  • Each NGINX pod counts on its own, so the effective limit is up to 2× that.
  • Pods run the framework dev servers (Flask app.run, Node): one process per pod.
Pwn · TCP

Fresh process per connection

  • Each container runs socat TCP-LISTEN,fork, so every nc session gets its own copy of the binary on a PTY.
  • -T60: the connection drops after 60 s of no traffic.
  • The NLB spreads connections over 3 pods. No rate limit, no connection cap.
  • Players share each container's filesystem and kernel: a player who pops a shell is in the same container other players use.
Scoreboard · CTFd

One pod for everyone

  • 1 pod, 2 gunicorn workers, sessions in Redis, data in MariaDB.
  • It handled the peak hour: 1,962 submissions between 10:00 and 11:00 SGT.
  • No rate limit in code at HEAD. A 100 rps limit was added on 06-26 and later reverted.
  • Upload limit 50m per request.
Per-IP limits may have been per-NLB-node inferred

The ingress NLB uses ip targets with plain TCP, and the repo sets neither proxy protocol nor client-IP preservation. In that setup AWS rewrites the source address to the NLB's own private IP, so NGINX would see one IP per AZ instead of each player. The "per IP" buckets of 20 rps and 15 connections would then be shared by every player routed through the same AZ. The audit's finding that CTFd saw all 9,316 submissions arrive from just 2 internal IPs fits this. It is a plausible contributor to the web downtime that led to the 15-minute extension, but it was never confirmed live.
